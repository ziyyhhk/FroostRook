# Kiwa 2.0

<img src="assets/kiwa.png" alt="Kiwa" width="220" align="right">

[![build](https://github.com/ziyyhhk/kiwa-engine/actions/workflows/build.yml/badge.svg)](https://github.com/ziyyhhk/kiwa-engine/actions/workflows/build.yml)

A chess engine built from scratch: a C++17 search core (0x88 board, alpha-beta
with a transposition table, hand-made evaluation) behind a JavaScript front-end
that supplies the UCI protocol, a 3,865-line opening book and a "predict the
human's next move" mode.

Prebuilt Windows binaries are on the
[Releases page](https://github.com/ziyyhhk/kiwa-engine/releases); every push also
builds one in GitHub Actions.

It is a real engine, not a wrapper around Stockfish. It is also not Stockfish —
more on that at the bottom.

## Quick start

Requires Node 18 or newer. Download the Windows build from
[Releases](https://github.com/ziyyhhk/kiwa-engine/releases) and save it as
`native/kiwa-native.exe`, or compile it yourself with `native\build.bat`
(MSYS2 UCRT64 GCC, one command; the local build is tuned for your CPU, release
builds are portable). Without the executable everything still works: `uci.js`
falls back to the JavaScript engine silently.

```bash
node uci.js        # UCI engine (GUIs, lichess-bot)
node play.js       # terminal, you are White
node play.js black # terminal, you are Black
```

On Windows, `kiwa.bat` does the same as `node uci.js` for GUIs that want a
double-clickable executable. All commands must run from this folder (the front-end
locates `book.js` and `native/` relative to its own path).

`play.js` still runs the JavaScript engine directly; the UCI path (`node uci.js`,
`kiwa.bat`, lichess-bot) uses the native core when present.

In terminal play mode, type moves in UCI notation (`e2e4`, `e7e8q` for
promotion). Commands: `hint`, `predict`, `moves`, `undo`, `new`, `depth N`,
`quit`. After each reply Kiwa prints its top three guesses for your next move.

## What changed in 2.0

| Change | Evidence |
|---|---|
| C++17 search core, ported line-for-line from `engine.js` | same perft counts on all 26 checks; mate and smoke tests agree |
| ~3–4× faster search | depth 12 from start: 0.34–0.49 s / 652,503 nodes / 1.3–2.0 M nodes/s (JS fallback in the same session: 1.28 s / ~0.52 M nodes/s) |
| More depth per move | WAC 1 s/move: 260/300 (86.7%); at 300 ms: 236–248/300 over three runs, vs 233/300 for JS 1.3 at 300 ms |
| Real UCI `stop` | search runs on a worker thread; `stop` joins it and answers with the best move so far (measured: 519–639 ms on a 30 s search) |
| Book consulted through move 20 | was 12; keeps Kiwa in named theory longer before the search takes over (where the database has data) |
| Node ↔ native bridge with fallback | `native.js` keeps one UCI child process and replays the full move history, so repetition and the 50-move rule survive the handoff; if the exe dies, the JS engine answers instead |

The native core deliberately contains no evaluation "upgrades" the JS version
does not have. It is the same engine, compiled: same PSTs, same pawn hash, same
LMR table, same time manager. That keeps the two implementations honest with
each other and makes every earlier measurement still meaningful.

## What changed in 1.3

| Change | Evidence |
|---|---|
| Pawn-structure hash + extras cache | depth 12 from start position: 2.5 s → 1.2 s, 1.08 M → 0.66 M nodes |
| Log-based LMR table | WAC 224 → 233/300 at 300 ms/move |
| Clock-aware time management | stability exit, next-iteration prediction, hard cap at 1.5× budget |
| Version bump | `id name Kiwa 1.3` |

Futility pruning and late-move pruning were tried and **rejected**: they saved
nodes but cost tactical accuracy on WAC (223–219 vs 233/300). Depth 12 from the
start position took 2.5 s and 1.08 M nodes before the pawn hash, 1.2 s and
0.66 M nodes after (roughly 530 k nodes/s, Node 24, single thread).

## Opening book

`book.js` is generated by `test/gen-book.js` from the
[lichess-org/chess-openings](https://github.com/lichess-org/chess-openings)
database (CC0): every named opening in it, from the Ruy Lopez and Najdorf to the
Latvian Gambit, the Evans Gambit, the Budapest, the Benko, the Grob.

- Keyed by board, side to move and castling rights, so transpositions share an
  entry and are recognised regardless of move order.
- Weights are the square root of how many named lines play a move, so main lines
  dominate but rare gambits still appear. Replies are drawn randomly by weight,
  so repeat games do not look identical.
- Used by the UCI front-end and `play.js` only. The search never reads it, so
  tactical benchmarks measure the search, not the book.
- When the opponent leaves the book, Kiwa starts searching. It does not try to
  "remember" the rest of a line it has not seen.

Validate every stored move with:

```bash
node test/book-check.js
```

Rebuild after editing `book-data/*.tsv`:

```bash
node test/gen-book.js
node test/book-check.js
```

## Play it against something

**Any UCI GUI — Cute Chess, Arena, BanksiaGUI, Lucas Chess, Chessbase:**
add an engine and point it at `kiwa.bat` (or `node uci.js` with this folder as
the working directory). Kiwa speaks standard UCI: `uci`, `isready`, `position`,
`go` with `movetime`/`depth`/clock fields, `bestmove`, plus `info` lines.

There are two valid engine files:

- `kiwa.bat` — the full engine. It starts Node, which adds the opening book and
  prediction mode around the native search. Use this one for normal play.
- `native/kiwa-native.exe` — the search core on its own. It is a complete UCI
  engine and needs no Node, so a GUI can import it directly, but it does not
  read `book.js` and therefore plays no book lines. This is the file attached
  to the GitHub release; useful for engine testing or machines without Node.

**Lichess — officially supported, but as a bot account.** Lichess has no
"upload an engine" button and the web analysis board cannot load a local engine.
What works is their bot API. A ready setup lives in `../lichess-bot/`
(dependencies installed in its own `.venv`; `config.yml` already points at
Kiwa):

1. Create a normal Lichess account, e.g. `KiwaBot`.
2. Go to <https://lichess.org/account/oauth/token>, create a token and tick
   **Play games with the bot API (`bot:play`)**. Copy it.
3. Paste the token into `../lichess-bot/config.yml` (or set the
   `LICHESS_BOT_TOKEN` environment variable instead of storing it in the file).
4. Run `../lichess-bot/upgrade-to-bot.bat` **once**. This converts the account
   to a bot account through Lichess and is irreversible.
5. Run `../lichess-bot/start-kiwa-bot.bat` and leave the window open. Kiwa
   appears at `lichess.org/@/YourBotName`, accepts challenges, and after about
   five idle minutes starts challenging other bots itself.
6. Upload `assets/kiwa.png` as the profile picture on the Lichess account page —
   that is where an engine's avatar lives, since UCI has no such field.

Notes: bots cannot play rated games against humans (only unrated), bot-vs-bot
play is capped at 100 games/day, and the bot is offline whenever this computer
is asleep or the window is closed. `ponder: false` is deliberate — Kiwa starts
searching only when it receives `go`; it does not ponder on the opponent's clock.

**chess.com — no.** There is no API for third-party engines, and joining games
with a script violates their terms. Do not try to bridge the board; accounts get
closed.

**Chessify / Chess Compass — no custom engines.** They are cloud analysis
platforms running their own Stockfish builds (Chessify advertises Stockfish 18
and 19). There is no import path for a local UCI engine.

**Strength estimate:** the honest way is a local match against Stockfish in
Cute Chess: add `kiwa.bat` as one engine, a Stockfish binary as the other, and
run 100 games at 1 s + 0.01 s. Losing by several hundred Elo would be normal for
a handcrafted engine. No calibrated Elo has been measured. The native core
searches about 3–4× faster and solves 260/300 WAC positions at 1 s/move, but
that is not an Elo rating, and no game result against Stockfish has been
recorded yet.

## Human-move prediction

`predict` ranks every legal move by a blend of depth-5 search score and priors
for what humans actually play — opening frequencies, captures, checks, castling,
development. Scores become probabilities through a softmax.

Measured on two real games, every ply a target (both sides human):

| Game | Top-1 | Top-3 |
|---|---|---|
| Morphy, Opera Game (1858), 33 plies | 21/33 (63.6%) | 26/33 (78.8%) |
| Anderssen–Kieseritzky, Immortal Game (1851), 45 plies | 24/45 (53.3%) | 31/45 (68.9%) |
| Combined, 78 human moves | 45/78 (57.7%) | 57/78 (73.1%) |

That is the honest number: it is a human-move model, not mind-reading. It misses
sacrifices and unusual plans, which is most of why the Immortal Game scores lower
than the Opera Game.

```bash
node test/predict.js 5 30 1    # depth 5, temperature 30, prior scale 1
```

## How it works

The search and evaluation live in `native/kiwa.cpp`; `engine.js` is the same
engine in JavaScript and is used as a fallback, by `play.js`, and by the test
helpers that need to parse SAN. `native.js` keeps one native process alive and
speaks UCI to it; the Node front-end never touches the native internals.

- **Board**: 0x88 array, Zobrist hashing, incremental material/PST scores.
- **Evaluation**: pawn-structure hash (doubled, isolated, passed), an extras
  cache for the remaining terms, tapered midgame/endgame piece-square tables,
  bishop pair, rooks on open/semi-open files and on the seventh, king pawn
  shield, tempo.
- **Search**: iterative deepening with aspiration windows, principal variation
  search, transposition table (2 M entries, 64-bit keys natively), null-move
  pruning, log-table late move reductions, check extensions, quiescence search
  with delta pruning, killer moves, countermoves, history heuristic with aging,
  reverse futility pruning, mate-distance-safe scoring. Identical decisions in
  both implementations.
- **Time management**: clock-based budget (default: about 1/50 of the remaining
  time plus increment), an early exit when the best move has been stable for two
  iterations, a check that skips iterations that cannot finish in the budget,
  and a hard cap at 1.5× the soft budget so `bestmove` always beats the flag.
- **Book**: see above. Weighted, FEN-keyed, outside the search.
- **Prediction**: depth-5 search of every legal move, blended with human priors.

## What this is not, and what it would take

Stockfish is roughly 3700 Elo: NNUE evaluation over billions of trained
positions, SIMD-optimised C++, years of tuning. AlphaZero needed thousands of
TPUs and millions of self-play games. Kiwa is a handcrafted engine — a C++ port
of a JavaScript engine — with a name database, not a neural network.

Honest gaps:

- **Speed**: ~2 M nodes/s here vs tens of millions for Stockfish.
- **Evaluation**: handcrafted terms vs a trained neural network.
- **Tuning**: no SPSA or large-scale self-play tuning; changes are measured on
  WAC and short matches, which have real noise.
- **Testing**: no CCRL/gauntlet rating, no matches against strong engines.
- **Book**: opening theory only. Kiwa does not know endgame tablebases.
- **Prediction**: tuned on two 19th-century games; a modern-game set would be a
  better test.

The C++ port is done (2.0). The realistic path from here, in order of payoff:
replace the handcrafted evaluation with an NNUE trained on public data, add
multithreaded search and Syzygy, tune parameters with SPSA/self-play, then run
gauntlets on CCRL to get an actual rating. The top single-author engines sit
roughly 100 Elo behind Stockfish after years of that work.

## Known limitations

- The native core answers `stop` properly (the search runs on a worker thread).
  The JavaScript fallback is synchronous: no `stop`, and `go infinite` is capped
  at 20 seconds there.
- The search itself is single-threaded in both cores; the native thread exists
  only so `stop` can interrupt it. No pondering, no Syzygy.
- The prebuilt exe was compiled with `-march=native`. Rebuild with
  `native\build.bat` if you move the folder to a different CPU.
- No `setoption` support (Kiwa has no tunable options, so nothing to set).
- The book is only consulted in the first twenty moves, and only when the search
  is not explicitly depth- or node-limited (i.e. not during analysis).
